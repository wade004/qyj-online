# 《群英决》PC 联机大厅、玩家系统与房间交互草稿

> 文档状态：交互草稿 v1.0<br>
> 日期：2026-07-11<br>
> 设计基准：1440×900<br>
> 最低完整保障：1024×640<br>
> 原则：本期不改变 1–3 名真人、AI 补足 6 人、12 回合、房主直接开始选将的现有规则

> 实施状态（2026-07-11）：PC v2 大厅、游客档案、房间、选将、统一错误反馈、离线成员状态及 90 秒会话恢复均已实现，并通过 PC/H5 混合房完整自动化对局。生产发布前仍需完成目标环境真机/桌面视觉验收与灰度操作。

## 1. 设计结论

当前 PC 联机页面属于功能验证界面，不适合继续在原结构上局部修补：

- 大厅内容缩在页面中央，空间利用率和文字对比度都很低；
- 房间只有队名、人数、状态和按钮，缺少稳定导航、身份信息和操作反馈；
- “玩家系统”实际只有每次连接随机生成的临时代号，没有账号、稳定 ID、头像、持久化或战绩；
- 改名、创建、加入、开始等操作缺少明确的 pending / ack / reject；
- online.js 同时负责 WebSocket、状态机和 DOM，PC/H5 若继续共改同一文件，回归风险很高。

本期 PC 目标不是建设完整账号平台，而是先完成：

1. 一套稳定的 PC 联机外壳；
2. 可用的队伍大厅；
3. 明确标识为“游客档案”的最小玩家身份；
4. 信息清楚、操作有反馈的房间页；
5. 与 H5 共用规则和会话、但完全分离视图与样式。

## 2. 本期范围

### 2.1 本期交付

- PC 联机统一顶栏与页面导航；
- 大厅队伍列表、全部/可加入筛选、房间号加入、创建队伍；
- 游客档案：稳定纹章、昵称、短玩家编号、当前状态、网络状态；
- 自己的玩家中心、其他玩家的公开资料；
- 房间号、真人席位、房主/成员/本人/空位、AI 补位摘要；
- 房主开始选将、普通成员等待、退出确认与房主自动移交说明；
- 创建、加入、改名、开始、退出的提交中与失败状态；
- 加载、空、已满、选将中、对局中、断线、房间解散等状态；
- PC/H5 双端隔离和双端回归门禁。

### 2.2 本期不做

- 注册登录、手机号或第三方账号；
- 跨设备档案同步；
- 好友、私聊、邀请、举报、黑名单；
- 历史战绩、段位、排行榜、成就；
- 准备/取消准备；
- 房主踢人、手动转让、密码房、观战；
- 自定义人数、AI 难度或玩法规则。

页面不得展示虚假的场次、胜率或段位。没有持久化后端之前，必须明确写“游客档案 · 仅本机保存”。

## 3. PC 与 H5 并存架构

### 3.1 入口隔离

~~~text
/index.html  → PC 入口 → PC UI + pc.css
/h5.html     → H5 入口 → H5 UI + h5.css + 横屏控制
                           ↓
                 Shared Application Layer
          OnlineSession / ViewModel / Commands / Protocol
                           ↓
              Engine / RemoteEngine / Game Rules
~~~

不可妥协项：

- PC 根入口永久不自动转成 H5；窄窗口、触屏笔记本和竖屏显示器仍然是 PC。
- H5 的 requestFullscreen、orientation.lock 和竖屏阻断不能进入 PC 依赖图。
- 平台由入口启动配置决定，不用 UA 或 viewport 做平台判断。
- PC/H5 共享同一个 OnlineSession 和协议适配器，不复制 WebSocket 状态机。
- PC 与 H5 的 DOM、弹层、交互手势和 CSS 不共享。

### 3.2 迁移顺序

1. 先给当前 PC 建浏览器流程与截图基线；
2. 从 online.js 抽出无 DOM 的 OnlineSession，旧 PC UI 1:1 接回；
3. 确认现有 PC 行为无变化；
4. 开发 PC 大厅/玩家/房间 v2；
5. 独立开发 H5 视图；
6. 最后接入断线恢复和混合端回归。

不要在现有 online.js 里一边重做页面、一边修改连接状态机。

### 3.3 CSS 与资源

- PC 新样式限定在 .pc-online 下，组件采用 pc-lobby__*、pc-room__*、pc-player__*；
- H5 只使用 .h5-*；
- 禁止新写裸 button、.screen、.result-row 等全局选择器；
- 共享 CSS 只保留 token 和最小 reset；
- PC 保留高分辨率人物资源；H5 使用新增的 WebP/AVIF 与缩略图，不覆盖同名文件；
- PC v2 与 H5 使用独立功能开关，可分别发布和回滚。

## 4. PC 联机全局外壳

1440×900 基准结构：

~~~text
┌──────────────────────────────────────────────────────────────────────┐
│ 群英决 · 联机 │ 返回首页 │ 联机大厅 / 房间      在线 42ms │ 玩家档案 │
├──────────────────────────────────────────────────────────────────────┤
│ 网络异常横幅：仅异常时出现，保留当前页面，不替换为空白连接页         │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│                           当前页面内容                               │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
~~~

全局交互：

- 顶栏不随大厅/房间页面重新渲染，身份和网络状态始终可见；
- 点击右上玩家档案打开 420–480px 右侧抽屉；
- 在线、弱网、重连中、离线同时使用图标和文字；
- 可修复错误放在对应操作附近，系统级错误使用顶部横幅；
- 成功反馈使用右下 toast；
- Escape 关闭顶层弹窗/抽屉，关闭后焦点回到触发按钮；
- 所有写操作提交期间锁定重复点击。

│                                                   │ 网络：在线 42ms  │
│ 队伍            真人      状态           操作    │ [编辑游客档案]   │

1024–1279px 紧凑桌面：右侧信息栏移到房间列表下方，但列表、创建和加入入口必须保留。

### 5.2 房间列表

每行只显示决定是否加入所需的信息：

- 队伍名称与房间号；
- 真人数量 N/3；
- 待命、已满、选将中、对局中；
- 加入或明确禁用原因。

默认排序：可加入优先，其次按房间号倒序。大厅使用服务端推送实时更新，刷新按钮只作为异常恢复入口。

### 5.3 筛选与房间号加入

- “全部”展示所有公开队伍；
- “可加入”只展示待命且未满队伍；
- 输入房间号后直接调用 join(teamId)；
- 房间不存在、已满或已开始时保持大厅，行内/输入区显示原因；
- 加入中锁定其他加入入口，成功后进入房间。

### 5.4 创建队伍

本期保持现有规则，不开放自定义玩法：

~~~text

│ 队伍名称和编号由系统生成                  │
│                                           │

│ 真人上限       3 名                       │
│ AI 补位        补足至 6 名                │
│ 赛制           固定 12 回合               │
│                                           │
│                         [取消] [确认创建] │
└───────────────────────────────────────────┘
~~~

创建流程：

~~~text
确认创建 → 按钮“正在创建” → 服务端确认 → 进入房间
                               └→ 失败：弹窗保留并显示原因
~~~

### 5.5 大厅状态

| 状态 | 页面表现 |
|---|---|
| 首次加载 | 房间行骨架，不提前显示空态 |
| 无队伍 | “暂无公开队伍”与创建队伍按钮 |
| 筛选无结果 | “当前没有符合条件的队伍” |
| 加入中 | 当前行按钮显示“正在加入”，其他加入入口锁定 |
| 房间刚满 | 行更新为已满，保持大厅 |
| 重连中 | 保留旧列表并标记可能过期，写操作锁定 |
| 维护/版本不兼容 | 顶部阻断横幅与重试/刷新 |

## 6. 玩家系统交互草稿

### 6.1 当前事实

当前代码没有真正的玩家系统：

- 每次 WebSocket 连接随机生成代号；
- 只支持 1–8 字改名；
- 没有稳定 playerId、认证、头像、持久化或战绩；
- 刷新、重连或服务重启后身份丢失。

因此本期先建设“游客档案”，而不是伪装成正式账号系统。

### 6.2 自己的玩家中心

~~~text
┌──────────── 玩家中心 ────────────┐
│ [纹章]  燕云骑                   │
│         游客档案 · 仅本机保存    │
│                                  │
│ 选择纹章  [云] [羽] [墨] [月]   │
│ 昵称      [燕云骑              ]│
│           1–8 个字符             │
│                                  │
│ 玩家编号  #A82F                  │
│ 当前状态  大厅中                 │
│ 网络状态  在线 · 42ms            │
│ 跨设备    暂不支持               │
│                                  │
│                   [取消] [保存]  │
└──────────────────────────────────┘
~~~

字段：

- 稳定纹章：内置图形或按本地 guestId 生成，不与本局英雄头像混淆；
- 昵称：沿用 1–8 字规则，允许重名；
- 短玩家编号：用于同名区分和房间内识别；
- 当前阶段与网络状态；
- “仅本机保存”的明确说明。

保存流程：

~~~text
编辑 → 本地校验 → 保存中 → 服务端确认 → 顶栏/大厅/房间/选将同步更新
                         └→ 断线：保留草稿，恢复后再同步
~~~

### 6.3 查看其他玩家

点击房间成员，打开只读公开资料：

- 纹章、昵称、短编号；
- 房主/成员身份；
- 在线、弱网、重连中状态；
- 当前所在阶段。

不展示暗令、私密技能结果，也不展示尚未持久化的战绩数据。

### 6.4 后续正式账号

若后续建设登录、跨设备、战绩或段位，需要独立的数据与安全设计，至少包含 users、auth_sessions、player_profiles、matches、match_players。本期游客档案不得阻塞未来升级，但也不预埋虚假 UI。

## 7. 房间页交互草稿

### 7.1 布局

~~~text
┌──────────────────────────── 顶栏 ────────────────────────────────────┐
│ 返回大厅   长风营 #1048   待命                在线 42ms [燕云骑▼] │
├───────────────────────────────────────────────┬──────────────────────┤
│ 真人席位 2/3                                  │ 本局信息             │
│ 2名真人，开局后由4名AI补位                    │ 真人 2/3            │
│                                               │ AI 4名              │
│ ┌──────────┬──────────┬──────────────┐         │ 总人数6 · 12回合    │
│ │ 燕云骑   │ 墨者     │ 等待玩家加入 │         │                    │
│ │ 你·房主  │ 成员     │ 空位         │         │ 房间动态           │
│ │ 在线     │ 在线     │              │         │ 创建 / 加入 / 改名 │
│ └──────────┴──────────┴──────────────┘         │ 房主转移 / 开始     │
│                                               │                    │
│                                               │ [开始选将]         │
│                                               │ [退出队伍]         │
└───────────────────────────────────────────────┴──────────────────────┘
~~~

### 7.2 席位状态

| 状态 | 表现 |
|---|---|
| 自己且为房主 | 纹章、昵称、编号、“你”、房主标识、网络状态 |
| 自己且为成员 | “你”、成员标识、网络状态 |
| 其他成员 | 昵称、编号、网络状态；点击查看公开资料 |
| 弱网/重连 | 图标 + 文字；不能只变色 |
| 空位 | “等待玩家加入”，不提前显示为 AI |
| AI 补位 | 只在房间摘要显示“开局后由 N 名 AI 补位” |

本期不引入准备状态。页面明确提示“房主可直接开始选将，无准备环节”。

### 7.3 房主操作

- 主按钮：“开始选将”；
- 辅助说明：“当前 N 名真人，开局后 AI 补足至 6 人”；
- 点击后进入“正在开始”，收到服务端状态后全员进入选将；
- 请求失败时保持房间并恢复按钮；
- 若存在重连保留中的真人，按钮锁定并解释原因。

### 7.4 普通成员

- 不展示不可用的伪主按钮；
- 明确显示“等待房主开始选将……”；
- 房主离开并自动转移后，页面实时切换为房主操作区，并提示“你已成为房主”。

### 7.5 房间动态

房间动态是系统事件，不是聊天：

- 创建、加入、离开；
- 改名；
- 房主自动转移；
- 重连成功；
- 开始选将。

事件可由客户端比较连续房间快照生成；无需本期建设聊天系统。

### 7.6 退出队伍

普通成员：

~~~text
退出后返回联机大厅，确定退出？
~~~

房主且仍有成员：

~~~text
退出后房主将自动移交给墨者，确定退出？
~~~

最后一名成员退出后房间销毁。确认退出期间按钮进入 pending，成功后再返回大厅。

### 7.7 房间异常

| 状态 | 处理 |
|---|---|
| 断线 | 保留房间，顶部重连横幅，写操作锁定 |
| 重连成功 | 拉取最新快照，提示“已恢复至最新状态” |
| 房间解散 | 返回大厅并解释原因 |
| 房主转移 | 更新席位和操作区，增加系统事件 |
| 开始被拒 | 保持房间，恢复按钮并显示结构化原因 |
| 成员成为幽灵 | 上线前修复服务端断线成员清理/恢复逻辑 |

## 8. 现有协议与新增范围

### 8.1 当前可直接复用

| 交互 | 当前能力 |
|---|---|
| 获取大厅 | lobby 事件的 teams[] |
| 队伍名/号/人数/阶段 | id、name、count、phase |
| 创建队伍 | create |
| 按房间号加入 | join(teamId) |
| 离开队伍 | leave |
| 修改昵称 | rename(name) |
| 房间成员/本人/房主 | team 事件 members[] |
| 房主开始选将 | startPick |
| 战后回房 | backToRoom |

### 8.2 最小新增协议

为了让上述交互达到上线标准，需要新增：

- 稳定 guestId/playerId 与短编号；
- profile 中的 nickname/avatarKey；
- requestId + ack/reject + errorCode；
- protocolVersion、seq、serverNow；
- sessionId/resumeToken 与断线恢复；
- 成员在线/弱网/重连状态；
- 结构化创建、加入、改名、开局失败原因；
- 绝对选将 deadlineAt。

协议只做向后兼容新增，旧 PC 客户端至少保持 N-1 可连接。

## 9. 双端回归矩阵

### 9.1 PC

- 1024×640、1280×720、1366×768、1440×900、1920×1080；
- Chrome、Edge，至少一轮 Firefox；
- 鼠标 hover、键盘、Windows 125% 缩放；
- 窄窗口、竖屏显示器仍为 PC，绝不能出现 H5 横屏提示。

### 9.2 H5

- 568×320、667×375、844×390、915×412；
- iOS Safari、Android Chrome；
- safe-area、地址栏伸缩、触控无 hover；
- 任何竖屏状态都只显示 H5 阻断层，旋回横屏后不重复连接或发命令。

### 9.3 混合端完整流程

必须覆盖：

- PC 房主 + H5 成员；
- H5 房主 + PC 成员；
- 大厅 → 创建/加入 → 修改游客档案 → 房间 → 选将 → 对局 → 结算 → 回房；
- 房主离开、同名玩家、断线恢复、后台恢复；
- 两端看到一致的房间成员、选将占用、行动、主/边池和结算。

### 9.4 PR 门禁

- 现有 npm test；
- 跨层 import 规则；
- CSS 无未定义 token、无 H5 全局选择器；
- PC/H5 浏览器 smoke；
- PC v2 视觉基线；
- 混合端 WebSocket E2E；
- H5 横竖屏恢复；
- 无 console error / unhandled rejection。

## 10. 实施顺序

1. 建立 PC 旧版视觉与流程基线；
2. 抽离 OnlineSession，旧 PC 1:1 回接；
3. 完成 PC 联机外壳、游客档案和大厅；
4. 完成房间页、系统事件、pending/error；
5. 增加玩家/会话最小协议；
6. 接入 H5 独立入口和独立 UI；
7. 完成 PC/H5 混合端与真实设备回归；
8. PC v2、H5 分别灰度，任一端可独立回滚。

## 11. 评审决策

进入高保真和开发前建议确认：

1. 玩家系统本期先做“游客档案”，不展示战绩/段位；
2. 房间继续沿用“无准备、房主直接开始、AI 自动补位”的现有规则；
3. PC 使用稳定入口，H5 使用独立入口，不做 viewport 自动切换；
4. 创建队伍仍由系统生成名称，本期不开放自定义规则；
5. PC/H5 混合房完整对局是上线阻断验收项。
